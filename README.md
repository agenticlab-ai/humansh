# humansh

`humansh` adds conservative natural-language command translation to ordinary interactive Zsh and Bash prompts. Provider output is inserted into the editable command line for review and is never executed automatically.

```text
% show me which process is listening on port 3000
lsof -nP -iTCP:3000 -sTCP:LISTEN
  Generated by Codex. Review it, then press Enter to run.
```

## Install

From a checkout:

```sh
./scripts/install.sh --local
```

Setup automatically detects and configures every supported shell available on the machine. Users do not need to know or select their current shell. To intentionally restrict an installation to one shell, use the advanced `--shell` option:

```sh
./scripts/install.sh --local --shell bash
# Or, after the binary is installed:
humansh setup --shell bash
```

Bash integration requires Bash 4.3 or newer so Humansh can safely capture and restore existing Readline shell-command bindings. macOS still ships Bash 3.2, so install a current Bash with, for example, `brew install bash`. The setup compatibility report shows each installed supported shell and version; for an unsupported Bash it shows the 4.3 minimum and continues with Zsh. Rerun `humansh setup` after installing a current Bash to add its integration.

Release installation is designed for:

```sh
curl -fsSL https://raw.githubusercontent.com/mdarabi/humansh/main/scripts/install.sh | bash
```

This downloads the installer directly from the GitHub repository, then installs the matching binary from the latest GitHub release after verifying its SHA-256 checksum. Forks can select their own release repository with `curl -fsSL https://raw.githubusercontent.com/OWNER/REPOSITORY/main/scripts/install.sh | HUMANSH_REPOSITORY=OWNER/REPOSITORY bash`. See [Security](docs/security.md) for the distinction between checksum integrity and release authenticity.

Setup verifies Zsh and Bash independently, installs the embedded integration for each usable shell under the XDG data directory, and adds an idempotent block to each applicable startup file:

```sh
humansh setup
```

Interactive setup is a guided review rather than a silent application of defaults. Its Shell compatibility phase lists only installed supported shells and concise versions; startup-file activation details are reserved for the final review. Slow discovery and provider checks show an in-place loader on a terminal; redirected output receives one stable `Checking…` line instead of animation. Setup also shows shell modes, provider/model, directory-context privacy, timeout, and shortcuts before writing anything. Zsh supports Smart Enter; Bash uses explicit translation because Readline cannot safely make Enter conditionally accept or replace the buffer. Choosing OpenRouter configures it inside the same setup: setup accepts the key without echo, validates the key and model capability, discloses one minimal metered compatibility check, and stages the result until final confirmation. At a shortcut prompt, type a readable value such as `Ctrl-G`, `Ctrl-X Ctrl-T`, or `Esc t`. The final review shows only the managed-block patches for applicable activation files, never unrelated shell configuration. Setup preserves startup-file symlinks, applies all shell changes transactionally, can be cancelled without changes, and refuses stale reviewed patches. Use `--yes` for deterministic non-interactive setup and `NO_COLOR=1` to disable styling.

If Codex, Claude Code, or Cursor CLI is installed but logged out, interactive setup offers to attach its official subscription-login command directly to your terminal. Humansh never collects the login secret.

Provider checks apply to a fresh subprocess, because that is what humansh starts for each translation. Interactive setup always shows a compact four-provider menu and asks what to use; the saved provider is only the default answer. Troubleshooting details stay hidden for providers you do not select. If multiple Claude or Cursor CLI installations are present in `PATH`, setup lets you keep automatic selection or pin one exact executable; shell aliases and the Cursor editor launcher are intentionally not used.

Setup requires one proven, ready provider and stops before writing credentials, configuration, or shell integration when none is selected. The required OpenRouter compatibility check runs automatically after the user selects OpenRouter and supplies its key and model; if the check fails, setup stops rather than producing an unusable installation. The installer replaces the binary atomically and restores the previous binary whenever interactive setup does not complete.

## Keys and shell modes

| Key | Zsh | Bash 4.3+ |
|---|---|---|
| Enter (`^M`/`^J`) | Classify as literal, natural language, or ambiguous. | Keep normal Readline `accept-line`; after translation, run reviewed low/medium-risk output. |
| Escape | Clear the editable line and cancel pending generated output. | Same. |
| Ctrl-G | Force translation. | Translate the current line for review. |
| Ctrl-X, Enter | Force literal execution and confirm high-risk generated output. | Same. |

Escape intentionally replaces its prior action in the supported ZLE or Readline keymaps. In vi insert mode, it clears the current unsubmitted line instead of entering command mode. Longer Escape-prefixed terminal and Alt sequences remain subject to the shell's key-sequence timeout. `Ctrl-G` replaces familiar abort/list-expansion behavior. Setup reports these collisions. Configure alternatives with:

```sh
humansh config set shell.force_translate_binding '^X^T'
humansh config set shell.force_literal_binding '^X^M'
humansh config set shell.clear_line_binding '^U'
humansh config set shell.smart_enter false
```

Each managed block exports these resolved values before sourcing its immutable, hashed shell asset. Open a new terminal after changing them. Run `humansh-bindings` in either shell to inspect active and captured bindings.

With Zsh `shell.smart_enter=false`, ordinary Enter keeps its previous ZLE binding. Bash always uses this explicit mode. When Humansh loads in an interactive Bash terminal, it prints one concise activation notice explaining that the configured force-translation shortcut (Ctrl-G by default) translates natural language while Enter runs normal Bash commands; sourcing the integration again in that session does not repeat the notice. After Ctrl-G translation, low/medium-risk output can run with Enter; high-risk output temporarily gates both Enter encodings and requires Ctrl-X then Enter. Editing a gated command reruns local analysis. Escape clears the line and gate. `humansh-off` restores captured bindings but refuses to disable an active high-risk gate.

While a provider is translating, both integrations animate a loader beside `Translating with <provider>…`. Pressing the configured clear-line shortcut (Escape by default) immediately cancels the active provider process tree and clears the unsubmitted text; the key is consumed instead of being replayed after translation. Ctrl-C cancels and restores the original editable text. This behavior is the same for every provider. The loader stops before the generated command, error, or cancellation guidance is shown.

Ambiguous input is preserved and never sent to a provider. Inspect the decision locally:

```sh
print -rn -- 'find all files modified today' \
  | humansh classify --shell zsh --first-token-kind command
```

Use local overrides for project commands or personal English prefixes:

```sh
print -rn -- 'deploy' | humansh classifier add-command
print -rn -- 'explain how to' | humansh classifier add-english-prefix
```

## Providers

- `codex`: requires saved “Sign in with ChatGPT” subscription authentication. API-key authentication is rejected.
- `claude`: requires a claude.ai subscription login. Console/API/cloud overrides are rejected.
- `cursor`: requires a Cursor browser login. `cursor-agent` is preferred, with `agent` as the compatibility fallback; API-key and custom-endpoint overrides are rejected.
- `openrouter`: explicit metered API-key mode. Setup requires a concrete model to pass the real strict-schema probe before saving it.

```sh
humansh provider list
humansh provider use codex
humansh provider test codex
humansh provider use cursor
humansh provider test cursor
humansh provider configure openrouter --model provider/model
```

Run `humansh provider` or `humansh provider help` for oriented command help and
examples. `humansh provider list` prints a compact readiness view and marks the
current provider; use `humansh provider list --json` when complete diagnostics
are needed by a script. `humansh provider select <name>` is accepted as an alias
for `provider use <name>`.

There is no silent fallback to metered OpenRouter.

CLI providers are selectable only when their applicable version floor and direct capability checks confirm every mandatory non-interactive isolation control. Every translation still supplies the complete isolation argument set; a rejected setting fails closed. See [providers](docs/providers.md) for provider-specific limits and account-backed behavioral release gates.

Interactive `humansh setup` handles OpenRouter configuration in place. The standalone `provider configure` command remains available for changing an already-configured OpenRouter model. Both flows first validate the key through the read-only key-status endpoint, then use read-only model metadata to require `structured_outputs` rather than basic `response_format` support. Incompatible models are rejected before model credits are used, with a link to OpenRouter's filtered compatible-model list. During setup, paste the next model ID directly into the repeated model prompt; there is no intervening yes/no question, and `back` returns to the AI-provider menu. The already-valid key is not rechecked for each model. A model that passes metadata automatically receives one minimal metered request against humansh's exact strict-output schema. Manually changing the model does not mark it proven; use either guided setup or `provider configure` for that.

## Diagnostics and uninstall

```sh
humansh doctor
humansh doctor --fix
humansh uninstall
```

Uninstall removes every installed shell integration while preserving configuration and credentials by default. `humansh uninstall --purge` removes them only after confirmation; declining that confirmation cancels the entire uninstall without changing files. Use `--yes` only for an intentional non-interactive purge. The standalone `sh scripts/uninstall.sh [--purge]` and `make uninstall` workflows remain available from a checkout. A child process cannot alter its parent shell, so restart a shell only when it already has Humansh loaded in memory.
